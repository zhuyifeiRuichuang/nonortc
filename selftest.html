④-a 真实网页 ICE 实测 唯一有证据力的判定轨

取样跑在 普通网页 里：向每个已打开的 http/https 网页注入隔离世界探针，枚举该页面真实可见的 ICE 候选。取样环境与页面同源、同权限、同网络栈（ICE 候选由浏览器网络栈产生，与 JS 世界无关），且隔离世界原型链独立、页面脚本无法篡改。
判定口径：出现明文私网 host 候选（10. / 192.168. / 172.16-31. / 127. / 169.254. / 100.64-127.）→ FAIL；仅有 mDNS 遮蔽的 *.local 候选 → 全局开启时应为 WARN（策略未落地），全局关闭时属正常；0 条候选 → disable_non_proxied_udp 已抑制非代理 UDP，本机地址不可见（代价是无代理环境下 WebRTC 不可用）；仅 relay 中继候选 → PASS。

④-b 扩展页 ICE 对照 特权来源，不作判定

本卡片在扩展页自身枚举候选。实测（Chrome 154，有头 / 无头一致）：chrome-extension:// 属特权来源，Chrome 对其既不施加 mDNS 主机名遮蔽，也不施加 webRTCIPHandlingPolicy，因此无论策略如何设置，这里恒会出现明文内网地址。这是浏览器对该来源的行为，不是防护失效，也不代表普通网页会泄漏 —— 防护效果请以 ④-a 为准。

怎么看：在页面内查找 Timezone、Local Time、System Language 等字段，其值应与你配置的代理时区 / 语言一致；再与页面显示的 IP 归属城市对照 —— 两者时区应当吻合。不吻合即「代理穿帮」：浏览器时区与出口 IP 属地对不上，是高级指纹最易识别的破绽。

⚠ 已知边界：browserleaks /javascript 页的 iframe.contentWindow 标签页读的是一个 <iframe sandbox="allow-same-origin"> 帧 —— 该帧的脚本执行被沙箱禁用，内容脚本无法注入，因此该标签页会显示宿主机真实时区 / 语言。这是 Chrome 层面的约束，任何基于 JS 覆盖的扩展都无法处理（实测已确认：普通 about:blank、srcdoc、blob: 帧均已覆盖）。用 window 标签页（默认）核对才有意义。

⑥ 网络层泄漏：DNS / 直连 / IPv6 / QUIC 扩展无法修复

以下向量发生在操作系统 / 代理客户端的网络层。Chrome 未向扩展开放任何 DNS、路由或网卡控制 API，本扩展在架构上无法干预。若检测工具显示「DNS 泄漏」或读到你的真实 IPv4 / IPv6，请按下表在代理侧处理：
向量典型现象在代理 / 系统侧的处理
DNS 递归泄漏检测工具显示解析器为本地 ISP DNSClash/Mihomo：enhanced-mode: fake-ip + 加密上游(DoH/DoT) + 开启 TUN 与 dns-hijack；改后执行 ipconfig /flushdns
分流直连「中国出口 IPv4」显示本机真实 IP，而代理出口为境外改用全局代理，或对目标域名强制 PROXY 并置于规则最前；用 TUN 全量接管
IPv6 泄漏出现本机真实 IPv6代理未接管 IPv6 时，在系统网卡关闭 IPv6；否则在代理侧配置 IPv6 接管
QUIC / HTTP3(UDP)仅 TCP 的代理下，HTTP/3 连接绕过代理直连chrome://flags/#enable-quic 设为 Disabled 后重启；或使用支持 UDP 的代理
说明：本扩展的 disable_non_proxied_udp 只约束 WebRTC 的 UDP，不约束 QUIC。完整说明见项目 README.md「网络层泄漏」一节。
判定标准：泄漏 ≠ DNS 与出口 IP 国家不一致。真正的泄漏是 DNS 查询被发给了你不打算让其知道你访问了什么的解析器 —— 即本地 ISP 解析器。它掌握你的真实线路，而你正用代理出口伪装位置，二者分离即为泄漏。
本地闭环验证（推荐，比第三方检测站更有证据力）：项目内含零依赖自检工具，直接向 Akamai 权威 DNS 反查「谁在替你做递归查询」—— DNS 查询天然无法被 HTTP 代理转发，因此这是最硬的证据。
python tools/dns-leak-check.py --expect-country US
仅用 Python 标准库，无需 pip 安装；输出网络出口、网卡 DNS、实际递归解析器及归属、ECS 披露情况与判定。修复后复测的通过标准是：递归解析器不再是本机 ISP，且与代理出口一致。
